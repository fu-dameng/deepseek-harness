一轮 Agent，究竟怎样跑起来？

DeepSeek Harness 不是一个“写死的聊天循环”。它把模型、工具、会话、沙箱和 UI 都装进可替换的 Cordis 插件树里；这一页沿着源码，追踪一次输入如何变成模型请求、工具结果，再回到下一步。

读完你应能解释为什么 session log 是“模型看到的上下文”；turn 和 step 的边界如何工作；工具为什么既能并行又仍按模型顺序提交；以及插件从哪里插入行为。
01 · 先建立地图

“一切皆插件”意味着什么？

Harness 的核心不是一个巨大的中心类，而是一棵按顺序叠加的配置树。每个能力有自己的服务接口、提供者和消费者；替换一个提供者，可以移动一整条能力链。

CORE

Profile / Bundle

Profile 列出 bundle；patch 可以替换某一配置行的整段配置。最终运行时是一棵可组合的 Cordis tree。

CORE

Capability seam

一项可替换能力至少有 Service Definition、Provider、Consumer 三个角色。

SOURCE

核心包

session、system-prompt、tools、agent、agent-loop、llm 共同构成主干；文件位置见下方 source map。

02 · 第一个关键区别

Turn 不是 Step

一个 step 是“一次模型请求加上它调用的工具”；一个 turn 可以包含零个或多个 step。工具结果或新的 steering 输入，可能让同一轮继续请求模型。

SOURCE · packages/core/agent-loop/src/agent.ts:245–328 · 每个 turn 先 append turn/start，每个 step 先 append step/start，最后写入对应 end。
为什么这样分层？

步骤是模型交互的原子单位

每次 step 都重新组装 prompt、tool schemas 和 deriveMessages()。这样插件可以在 agent/pre-step 改写或拒绝输入，也可以在 agent/request 介入路由。

SOURCE

第一步可以没有模型请求

如果首个 claim 被拒绝，或改写后变成空消息，turn 会以“无 step”关闭，但领取动作仍留在日志语义中。

03 · 上下文从哪里来

Session log 是模型上下文的单一来源

模型不是直接读取 UI 的实时对象。它看到的是由持久事件投影出来的 message history；原始 chunk 还保留在日志里，用于回放和 UI fidelity。

04 · 核心机制实验

工具可以并行，但结果仍按模型顺序提交

源码把连续的 parallel 调用放入有界滚动池；exclusive 调用是屏障。只有 dispatch/body 重叠，policy、result 和 additionalContexts 仍按模型顺序 commit。

教学用缩小示例

拖动并播放一次含 4 个工具调用的 step。这个实验不伪造真实工具结果，只展示源码中的调度规则。

观察问题：write 为什么会成为屏障？因为它被定义为 exclusive，调度器会先排空当前池，再单独运行它。

输入

ToolCallBlock

模型输出的是 { id, name, arguments }。参数先 JSON parse；无效 JSON 会保留为文本，空参数映射为 {}。

输出

tool/call → tool/result

每个已启动调用都会持久化 call/result 对；取消后未分发的调用也会补上 ABORTED_BEFORE_DISPATCH，保证回放仍有效。

三个最值得记住的插入点

agent/pre-step：决定模型本步看到什么。
agent/request：在分发前改写 provider/model/config。
tools/pre-execute：审批、沙箱、策略等在工具真正执行前介入。

为什么它适合扩展？

循环本身只负责“请求模型、运行工具、重复”。压缩、重试、权限、计划模式、UI、持久化等行为挂到事件和能力接缝上，彼此不必 import loop 内部实现。
