SOURCE-BASED INTERACTIVE TEXTBOOK · DEEPSEEK HARNESS · REBUILD 02
从一条输入开始

一次请求，如何穿过整个 Harness？

你输入一句话以后，系统并不是“调用模型然后结束”。输入先进入 inbox，驱动器打开一个 turn；它组装 prompt 和工具 schema，写入 session log，再把可回放的历史交给 LLM。模型若调用工具，结果又会成为下一步的输入。

本页的单一问题为什么 DeepSeek Harness 能把模型、工具、持久化、权限和 UI 替换掉，却仍然保持一条可追踪的 agent 主流程？

01 · 先建立问题

它要解决的不是“聊天”，而是可组合的执行

一个 agent 回合里，模型请求、工具副作用、取消、重试和 UI 回放必须互相对得上。Harness 的办法是：插件负责能力，session log 负责事实，agent-loop 只负责驱动边界。

图中颜色代表角色：金色是组合入口，绿色是可叠加层，红色是运行时树；底部四个 service 是 loop 依赖的接口，不是四个硬编码单例。

CORE

插件树

每个部分都是插件：模型适配器、工具注册表、session log、agent-loop、Web UI。插件通过服务和事件连接，并可以卸载时撤销 effects。

CORE

Capability seam

可替换能力由 Definition、Provider、Consumer 三个角色组成。只有 Provider 没有 Consumer，就还没有完成一条 seam。

SOURCE

Loop 的克制

agent-loop 只拥有“请求模型、运行工具、重复”的具体驱动逻辑；压缩、重试、权限和 UI 留在扩展点。

02 · 先拆 4 个词

Session、Turn、Step、Inbox 各自负责什么？

如果把这四个边界混在一起，后面所有流程图都会看起来像“模型调用了几次”。点击每个词，观察它在系统中的职责。

Session
一个可持久化的事件流。它不是“当前页面的状态”，而是后续请求可以重新投影出的事实来源。

先记接口，再记术语

输入
消息进入 inbox，有 target（next-step / next-turn）和 wakeup 语义。
边界
turn/step 写入 durable events，决定回放、取消和后续请求的坐标。
事实
session/event 持久化用户、assistant、tool 交互；live agent/* 事件用于在途拦截。
关键区别：一个 step = 一次模型请求 + 它调用的工具；一个 turn = 0 个或多个 step。工具结果被放进 next-step inbox 时，同一个 turn 可能继续。

04 · 为什么必须记日志

Session log 不是“存档”，而是模型上下文的协议

下一次 request 通过 session.deriveMessages() 得到历史。原始 chunk 用于回放和 UI fidelity，完整 assistant/message 是完成锚点。模型看见的内容必须能从 log 重建。

一个无工具 step 的事件账本

event它解决什么问题
turn/start打开本轮持久边界，给后续事件坐标。
user/message记录真正进入模型历史的消息。
step/start标记一次模型请求的开始。
request/header记录 provider/model/system/tools 的生效快照。
assistant/chunk*保存流式片段，支持 UI 回放和 replay。
assistant/message写入完整完成消息，并引用 chunk seq。
step/end闭合这一次请求的边界。
turn/end记录 completed / error / aborted 等结果。
TEACHING EXAMPLE · 具体 chunk 数量取决于模型流；这里的事件顺序来自 architecture.md 与 agent.ts。

05 · 工具不是黑盒

并行发生在 dispatch，顺序发生在 commit

源码的调度器同时解决两个相反的要求：安全的读操作可以重叠；模型看到的结果仍必须按照 tool-call 的原始顺序提交。拖动池大小，再播放这个教学用调用序列。

TEACHING EXAMPLE

并行池大小：2

序列：A read（parallel）→ B grep（parallel）→ C write（exclusive）→ D search（parallel）

等待执行：先问自己，C 为什么不能和 A/B 一起跑？

观察学习问题：C 是 exclusive，所以当前 parallel pool 必须先 drain；但 commit 仍会按 A → B → C → D 的模型顺序推进。

输入：ToolCallBlock

模型提供 id / name / arguments。源码先解析 arguments；空字符串是 {}，非法 JSON 保留为文本，避免在调度前丢掉原始调用。

SOURCE · tool-calls.ts:parseArguments / executeToolCalls

取消也必须可回放

已启动的调用会 drain 并提交；没启动的调用会生成 ABORTED_BEFORE_DISPATCH 结果。这样历史不会出现“call 没有 result”的断裂。

06 · 分支与失败

同一条主线，为什么能处理 retry、abort 和工具继续？

理解正常路径后，点击三个分支。每个分支都回答“哪些事实被写入 log、driver 是否继续、模型下一步还能看到什么”。

completed
没有 tool-call：step 返回 completed；没有 next-step 工作时，turn-stopping 后写入 turn/end。模型历史保持可投影。
SOURCE · agent.ts:step / request-error / turn() · 失败路径不是页面装饰，而是 durable outcome 的差异。
LOCAL

agent/request-error

LLM 失败先进入 waterfall；监听器返回 retry 才会重新 build request，否则错误关闭当前 turn。

LIVE

AbortSignal

取消控制当前准入操作和轮次；唤醒输入可能被 latch，dispose 则不会 latch。

DURABLE

turn/end

completed、aborted、error、max-tokens 等结果被记录，resume 才能理解一次 turn 是怎样结束的。

扩展点如何对应需求

换模型：注册 ctx.llm adapter。
加工具：注册到 ctx.tools，schema 加入 prompt。
加权限：监听 tools/pre-execute。
加压缩：观察 agent/pre-step 的上下文压力。
接 UI：从 session/event 渲染，并用 agent/* 观察 live state。
