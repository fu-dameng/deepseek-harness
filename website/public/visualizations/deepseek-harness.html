从一条输入开始

一次请求，如何穿过整个 Harness？

你输入一句话以后，系统并不是“调用模型然后结束”。输入先进入 inbox，驱动器打开一个 turn；它组装 prompt 和工具 schema，写入 session log，再把可回放的历史交给 LLM。模型若调用工具，tool/result 进入 model surface，driver 会在同一 turn 打开下一 step。

本页的单一问题为什么 DeepSeek Harness 能把模型、工具、持久化、权限和 UI 替换掉，却仍然保持一条可追踪的 agent 主流程？

01 · 先建立问题

它要解决的不是“聊天”，而是可组合的执行

一个 agent 回合里，模型请求、工具副作用、取消、重试和 UI 回放必须互相对得上。Harness 的办法是：插件负责能力，session log 负责事实，agent-loop 只负责驱动边界。

图中颜色代表角色：金色是组合入口，绿色是可叠加层，红色是运行时树；底部四个 service 是 loop 依赖的接口，不是四个硬编码单例。

CORE

插件树

每个部分都是插件：模型适配器、工具注册表、session log、agent-loop、Web UI。插件通过服务和事件连接，并可以卸载时撤销 effects。

CORE

Capability seam

可替换能力由 Definition、Provider、Consumer 三个角色组成。只有 Provider 没有 Consumer，就还没有完成一条 seam。

SOURCE

Loop 的克制

agent-loop 只拥有“请求模型、运行工具、重复”的具体驱动逻辑；压缩、重试、权限和 UI 留在扩展点。

准确的装配层序：空列表 → profile 中按顺序声明的 bundle layers → profile 的 cordis.patch.yml → home 级 cordis.patch.yml → argv 顺序的 --patch overlays → 启动器生成的 telemetry switch。后层可以覆盖前层同 id 条目的 config。

02 · 先拆 4 个词

Session、Turn、Step、Inbox 各自负责什么？

如果把这四个边界混在一起，后面所有流程图都会看起来像“模型调用了几次”。点击每个词，观察它在系统中的职责。

Session
一个可持久化的事件流。它不是“当前页面的状态”，而是后续请求可以重新投影出的事实来源。

先记接口，再记术语

输入
消息进入 inbox，有 target（next-step / next-turn）和 wakeup 语义。
边界
turn/step 写入 durable events，决定回放、取消和后续请求的坐标。
事实
session/event 持久化用户、assistant、tool 交互；live agent/* 事件用于在途拦截。
关键区别：一个 step = 一次模型请求 + 它调用的工具；一个 turn = 0 个或多个 step。工具结果本身会进入 model surface，使 step() 返回继续信号；additionalContexts 才会另外进入 next-step inbox。

04 · 为什么必须记日志

Session log 不是“存档”，而是模型上下文的协议

下一次 request 通过 session.deriveMessages() 得到历史。原始 chunk 用于回放和 UI fidelity，完整 assistant/message 是完成锚点。模型看见的内容必须能从 log 重建。

一个无工具 step 的事件账本

event它解决什么问题
turn/start打开本轮持久边界，给后续事件坐标。
step/start标记一次模型请求的开始。
user/message记录真正进入模型历史的消息。
request/header记录 provider/model/system/tools 的生效快照。
assistant/chunk*保存流式片段，支持 UI 回放和 replay。
assistant/message写入完整完成消息，并引用 chunk seq。
step/end闭合这一次请求的边界。
turn/end记录 completed / error / aborted 等结果。

推导：UI 的瞬时对象不是模型协议；可见输入进入 log 后，才能在 resume、fork、telemetry 和下一步中保持一致。
RAW LOG

原始事件：保留全部事实

turn/start · step/start
request/header · context
assistant/chunk*
assistant/message · tool/result

边界、配置快照与流式片段都留在日志里，供 replay、调试与 UI 使用。

MODEL SURFACE

表面事件：只选模型可见内容

user/message
assistant/message（含 tool-call）
tool/result

surface.ts 精确限定这三类。执行期的 tool/call 事件不是另一条模型消息。

DERIVED REQUEST

投影结果：恢复角色消息

role: user
role: assistant
role: tool

deriveMessages() 从 surface 重建下一次请求，而不是直接复制全部日志。

三个集合不要混为一谈：raw log 是事实全集；model surface 是模型协议的筛选层；derived messages 是发给 adapter 的最终投影。
05 · 工具不是黑盒

并行发生在 dispatch，顺序发生在 commit

源码的调度器同时解决两个相反的要求：安全的读操作可以重叠；模型看到的结果仍必须按照 tool-call 的原始顺序提交。拖动池大小，再播放这个教学用调用序列。

并行池大小：2

序列：A read（parallel）→ B grep（parallel）→ C write（exclusive）→ D search（parallel）

pool=2：max(120, 70) + 50 + 90 = 260ms

等待执行：先问自己，C 为什么不能和 A/B 一起跑？

观察学习问题：C 是 exclusive，所以当前 parallel pool 必须先 drain；但 commit 仍会按 A → B → C → D 的模型顺序推进。

继续下一 step 的真正条件：assistant 含 tool-call 时，工具执行并写入 tool/result；除非工具声明 concludesTurn，step() 返回继续信号，driver 即使没有额外 inbox 消息也会再开一个 step。additionalContexts 只是可选的 next-step 补充。

输入：ToolCallBlock

模型提供 id / name / arguments。源码先解析 arguments；空字符串是 {}，非法 JSON 保留为文本，避免在调度前丢掉原始调用。

取消也必须可回放

已启动的调用会 drain 并提交；没启动的调用会生成 ABORTED_BEFORE_DISPATCH 结果。这样历史不会出现“call 没有 result”的断裂。

06 · 分支与失败

同一条主线，为什么能处理 retry、abort 和工具继续？

理解正常路径后，点击四个分支。每个分支都回答“哪些事实被写入 log、driver 是否继续、模型下一步还能看到什么”。

completed
没有 tool-call：step 返回 completed；没有 next-step 工作时，turn-stopping 后写入 turn/end。模型历史保持可投影。
SOURCE · agent.ts:step / request-error / turn() · 失败路径不是页面装饰，而是 durable outcome 的差异。
LOCAL

agent/request-error

LLM 失败先进入 waterfall；监听器返回 retry 才会重新 build request，否则错误关闭当前 turn。

LIVE

AbortSignal

取消控制当前准入操作和轮次；唤醒输入可能被 latch，dispose 则不会 latch。

DURABLE

turn/end

completed、aborted、error、max-tokens 等结果被记录，resume 才能理解一次 turn 是怎样结束的。

自检 1：为什么 B 先完成，却不能先写入模型历史？

因为并行只改变 body 的执行时序。policy、post、finalize、结果提交与 additionalContexts 都保持模型声明顺序，否则下一次请求会看到一个与 assistant tool-call 顺序不一致的世界。

自检 2：没有 additionalContexts，工具之后还会有下一 step 吗？

会。只要 assistant 含 tool-call 且没有工具声明 concludesTurn，step() 就返回继续信号；additionalContexts 只是额外加入 next-step inbox 的上下文。

自检 3：为什么不把所有 session event 都发给模型？

request/header、chunk、边界与诊断事件对回放很重要，却不是对话角色消息。model surface 只投影 user/message、assistant/message、tool/result，避免把执行协议泄漏成模型内容。

现在可以把 Harness 复述为：一个由 durable log 提供事实、由 turn/step 驱动推进、由 capability seam 提供替换点、由有序工具流水线守住因果关系的执行系统。
